# Checklist Authority Reconciliation — Implementation Evidence

## Scope

This prerequisite reconciles the existing controlled Checklist aggregate before any prepared Aircraft/RPA checklist content is researched or authored. It adds no prepared DJI, CASA or organisation checklist content and makes no Product Maturity, Production, deployment or data change.

## Authority design and implementation

- One existing Checklist aggregate remains authoritative: templates, immutable versions, applicability, executions, evidence and corrective actions.
- `PLATFORM_SYSTEM` and `ORGANISATION` are explicit authority planes. Platform identities are customer read-only. Organisation versions can cite a Platform source version and exact source item, but inherited authority is accepted only when identity and governed item content match exactly.
- Exact inherited content validation covers authority class, prompt, response type, required/optional state, N/A policy, evidence requirement, selection options, criticality and finding prompt. Source provenance is generated by the server, not accepted from the customer payload.
- Applicability is relational and exact across organisation, Base, lifecycle, Mission, Aircraft, maintainable asset, system, component position, manufacturer/model and configuration. Unsupported Mission context fails closed.
- Start freezes the exact version, sections, provenance, applicability and asset context. A later published version does not invalidate or rewrite an already-started execution.
- Completion validates the frozen response schema, required answers, N/A rules, evidence and sign-off in one transaction, then records immutable findings, audit and outbox evidence.
- Findings remain `DEFECT_HANDOFF_PENDING`; this slice does not automatically alter Aircraft/Fleet serviceability, grounding, mission readiness or maintenance authority.
- Legacy generic execution and corrective-action commands are revoked from `service_role`. The only corrective-action mutation retained is a checked RESOLVED transition for an existing same-organisation action whose exact execution/item has an immutable finding, with current Base access, active resolver, optimistic concurrency, audit and outbox.
- Readiness selects only the latest effective exact version. Aircraft and equipment-kit requirements must match active Mission assignment. Fleet readiness-required publication fails closed until the repository has an authoritative Mission-to-Fleet deployment relation; Fleet checklist execution remains available through exact applicability without making a false readiness claim.
- Browser reads decode bounded Checklist projections and Mission executions fail closed. Mission UI scope is keyed by user, tenant, permissions, delegated support session, Mission, Base, Aircraft/asset and configuration; late requests cannot repopulate a changed scope.
- The authoring UI exposes only response types with truthful inputs (`CHECK`, `PASS_DEFECT_NA`, `YES_NO_NA`). The database retains governed numeric/text/selection capability for a later dedicated UI.
