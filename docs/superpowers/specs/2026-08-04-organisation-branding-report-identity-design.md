# Organisation Branding and Report Identity Design

**Status:** Approved architecture pending written-spec review  
**Requirement:** Production Beta organisation branding and report identity  
**Date:** 2026-08-04

## Objective

Make generated Mission documents visibly belong to the operating organisation while retaining mandatory Spray Command attribution. Extend the existing authoritative Organisation resource, introduce immutable logo versions and a shared server-side report artefact architecture, migrate Mission Pack generation onto it, and add the post-completion Mission Record.

This package is organisation branding, not full white-label capability.

## Governing boundaries

- PostgreSQL remains authoritative.
- The existing Organisation resource is extended in place; no duplicate business-profile resource is introduced.
- Organisation branding is tenant-owned and tenant-isolated.
- The organisation logo is shared across operating locations in Production Beta.
- Files use internal IDs and immutable versions, never permanent provider URLs.
- Reports are generated server-side from persisted evidence; unsaved browser state is never authoritative.
- Every generated report retains the non-removable footer `Generated by Spray Command`.
- Mission Pack and Mission Record share infrastructure but retain separate lifecycle rules, evidence scope and templates.
- Existing report artefacts and historical Mission evidence are never rewritten.

## Organisation business profile

The authoritative Organisation profile gains version-controlled fields for:

- legal business name;
- trading name;
- report display name;
- jurisdictional business identifier type and value, including ABN;
- registered and postal addresses;
- primary phone, email and website;
- optional report contact details;
- optional licence and accreditation details;
- active logo version reference;
- branding status and entitlement state;
- record version and update attribution.

Existing organisation fields remain valid. New optional fields are nullable so migration does not fabricate historical values. Updates use an expected record version and a trusted server command. Every accepted update creates an audit event and transactional outbox event.

## Logo evidence model

`organisation_logo_files` stores immutable logo versions. Each row records organisation, internal file ID, immutable version, original filename, detected content type, byte size, SHA-256 checksum, dimensions, storage adapter identity, provider object key, uploader, upload timestamp, provenance, validation result and report-safe rendition references where applicable.

The Organisation profile selects one active logo version. Replacing a logo inserts a new immutable file version and changes only the active selection. Removing a logo clears the active selection without deleting historical files. Reports already generated retain their captured branding snapshots.

Production Beta accepts PNG, JPEG and WebP up to 5 MiB and 6000 × 6000 pixels. Files are decoded server-side to verify actual type and dimensions. Aspect ratio is retained using contain-style placement. Transparent PNG/WebP backgrounds remain supported. SVG is deferred until a sanitisation and safe-rendering pipeline is separately proven; an SVG upload fails visibly rather than being stored as trusted branding.

Storage uses a private organisation-branding bucket through the storage adapter. Failed database retention triggers best-effort object cleanup. Authoritative records never expose the provider key as public identity.

## Permissions and entitlements

Explicit permissions are:

- `organisation.branding.read`
- `organisation.branding.manage`
- `reports.read`
- `reports.generate`
- `mission.pack.generate`
- `mission.record.generate`

Branding management requires `organisation.branding.manage`. Report access requires both the general report permission and the report-type permission where applicable. Trusted commands enforce organisation membership and permissions server-side; PostgreSQL RLS provides a second tenant-isolation boundary.

Branding behaviour is entitlement-driven with repository-controlled states:

- `BRANDING_UNAVAILABLE`
- `ORGANISATION_BRANDING`
- `ADVANCED_BRANDING` (future)
- `FULL_WHITE_LABEL` (future)

Fly The Farm receives `ORGANISATION_BRANDING` through its normal entitlement record. No identity, email address or tenant ID is embedded in application logic.

## Shared Report Branding service

The Report Branding application service resolves the Organisation profile, entitlement and selected logo version into a provider-neutral immutable contract:

- organisation legal and trading names;
- report display name;
- approved contact and accreditation details;
- logo internal file ID, version, checksum, content type and dimensions;
- mandatory attribution text;
- branding template version;
- resolution timestamp.

If branding is unavailable or no active logo exists, the service supplies a clean text-only organisation header. It never emits a broken image reference and never blocks otherwise valid document generation.

Every report copies this contract into its branding snapshot. Later profile or logo changes cannot alter the snapshot or the stored report file.

## Shared report artefact model

`report_artefacts` is an append-only version stream keyed by organisation, optional Mission, report type and report version. Each artefact stores:

- stable artefact ID;
- report type (`MISSION_PACK` or `MISSION_RECORD` initially);
- version number;
- evidence manifest;
- branding snapshot;
- template version;
- output internal file ID and file version;
- PDF checksum and byte size;
- status;
- request and idempotency key;
- requesting user and timestamps;
- generation start/completion timestamps;
- retry lineage;
- sanitised failure code and message.

Statuses are `REQUESTED`, `QUEUED`, `GENERATING`, `READY`, `FAILED` and `SUPERSEDED`. Report rows are append-only except for tightly controlled status transitions performed by the worker. A retry never overwrites a READY artefact and never silently reuses a failed output. The same idempotency key returns the existing request; an intentional regeneration uses a new key and version.

Report output files are immutable internal file versions stored privately through the file adapter. The database retains checksum, provenance and template identity.

## Generation workflow

1. An authorised user requests a report through the versioned API.
2. The trusted command validates permission, entitlement, Mission lifecycle and evidence availability.
3. In one transaction it allocates the report version, captures the evidence and branding manifests, creates a `REQUESTED` artefact, writes audit/outbox events, and enqueues generation through the transactional outbox.
4. A durable worker claims the job idempotently and transitions it to `GENERATING`.
5. The worker renders the versioned template using only the captured manifests and internal files.
6. The worker stores the PDF, calculates its SHA-256 checksum, and marks the artefact `READY` atomically with output metadata.
7. A failed attempt marks the artefact `FAILED` with visible, non-sensitive failure information and emits audit/outbox evidence.
8. The browser polls or refreshes report state and downloads a READY artefact through an authorised server endpoint.

The worker interface is provider-neutral and remains separately deployable from request/response functions. Production Beta may run the worker through the approved durable execution mechanism, but rendering and domain contracts remain independent of Vercel and Supabase SDKs.

## Mission Pack

Mission Pack is the regenerable operational planning document used before operations. Every generation creates a new immutable report artefact version. It captures the latest approved Planning and Pre-flight evidence at request time, including selected revisions for map, forecast, observed weather where available, aircraft, equipment, personnel, chemical plan, JSA, risk controls, readiness, Mission Authorisation and required documents.

The Mission Pack header uses the captured organisation branding. The footer contains mandatory Spray Command attribution, page number, report version, generation timestamp, artefact ID and abbreviated checksum reference.

Migrating Mission Pack does not delete or mutate existing `mission_pack_revisions`. Existing records remain valid. New generations create shared report artefacts and retain compatibility links to the existing Mission Pack revision/authorisation contract during migration.

## Mission Record

Mission Record is the permanent post-completion historical document. Generation is rejected until authoritative Mission Completion exists.

Its evidence manifest references exact immutable revisions for:

- Planning Evidence;
- Pre-flight Evidence;
- Operational Evidence;
- Completion Evidence;
- Mission Outcome Observations and their immutable file evidence;
- Customer Outcomes available at generation time.

Content includes Mission/business context, planned and operational geometry, weather, resources, planned and actual chemicals and water, JSA, triggered controls, readiness, authorisation, flight lines, telemetry and files, events, planned-versus-actual comparison, completion, outcomes, customer outcomes, evidence checksums, branding, report version and generation timestamp.

A Mission Record artefact is never regenerated in place. If additional post-Mission evidence warrants another formal record, an authorised user creates a new report version. Earlier artefacts remain permanently accessible and retain their original evidence and branding manifests.

## Report presentation

The shared layout contract provides:

- a clean header with aspect-ratio-safe logo, report display name, approved contact/accreditation details, report title and Mission/document identifier;
- consistent typography, spacing, map placement and evidence tables;
- clear identification of omitted/not-recorded optional evidence;
- a fixed footer with `Generated by Spray Command`, page number, version, timestamp, artefact ID and checksum reference.

Templates are separately versioned for Mission Pack and Mission Record. Organisation data changes do not change template identity.

## API and UI

The existing Organisation administration area gains a bounded Business Profile and Report Branding panel. Authorised administrators can edit profile details, upload/preview/activate/replace/remove a logo, view file requirements and preview the report header. The broader application shell and colours are unchanged.

The versioned API exposes organisation branding read/manage commands, logo upload/version selection, report request/status/history and authorised download. Existing Mission Pack public contracts remain compatible while their implementation moves to the shared service.

Mission UI retains Mission Pack generation in the pre-flight workflow. After completion it exposes Mission Record generation, status, download and version history. No UI action permits editing an artefact.

## Security and privacy

- Server-side authorisation and RLS both enforce tenant isolation.
- Report downloads require current authorised access to the owning organisation and Mission location.
- Private object keys and signed URLs are short-lived transport details only.
- File signatures, actual content type, size and dimensions are verified server-side.
- SVG is rejected in Production Beta.
- Rendering escapes untrusted text and does not fetch arbitrary remote resources.
- Failure details returned to users are sanitised.
- Audit events identify the actor and exact before/after active-branding selection.
- Outbox events contain internal identifiers, not secrets or signed URLs.

## Migration and compatibility

All changes are repository-controlled SQL migrations. Existing organisations receive nullable profile additions and retain current names. Existing reports and Mission Pack revisions are not rewritten. Permission and entitlement records are provisioned through normal catalogue/role mechanisms. Fly The Farm branding is enabled through data configuration after the general capability exists.

## Error handling

- Invalid logos fail before authoritative file activation.
- Upload storage failure creates no database file record.
- Database retention failure triggers object cleanup and no active-logo change.
- Stale profile/logo selection returns an optimistic-concurrency conflict.
- Missing logo produces a valid text-branded report.
- Incomplete Mission Pack evidence returns precise validation errors.
- Mission Record before Completion returns a lifecycle blocker.
- Generation failure remains visible as FAILED and never exposes a partial artefact as READY.
- Download of a non-READY or unauthorised artefact is denied.

## Verification and acceptance

Test-first verification covers schema contracts, immutable file versions, content validation, checksums, optimistic concurrency, permission denial, tenant and location isolation, entitlements, branding snapshots, append-only report versions, lifecycle rules, idempotent job claims, visible failures, audit/outbox records, compatibility and no local fallback.

Production acceptance requires:

1. Fly The Farm uploads and activates a real logo.
2. Branding persists through refresh, re-login and a second authorised session.
3. Unauthorised and cross-tenant access is denied.
4. Logo replacement creates a new immutable version; removal preserves history.
5. Invalid, malformed and unsupported files fail visibly.
6. Mission Pack generates as a new branded artefact version from selected Planning/Pre-flight evidence.
7. Mission Record cannot generate before Completion.
8. Mission Record generates after Completion from the full immutable lifecycle manifest.
9. Both PDFs display correct organisation identity and `Generated by Spray Command`.
10. Text-only reports generate cleanly without a logo.
11. Earlier artefacts retain their original branding after profile/logo changes.
12. New artefact versions use the new active branding.
13. Internal file IDs, checksums, template versions, manifests, audit and outbox evidence are retained.
14. Failed and retried generation is visible and never overwrites an earlier artefact.
15. Production tests, build, migration, deployment and live workflow verification pass without synthetic operational evidence.

## Deferred scope

This package does not add custom application identity, colours, login pages, domains, emails, legal identity replacement or removable Spray Command attribution. It does not add operating-location logo overrides or full white-label behaviour.
