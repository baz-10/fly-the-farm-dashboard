# Authoritative Mission JSA Design

**Status:** Product Owner approved 2026-08-03  
**Requirements:** IMP-MIS-004, NEW-SAF-001, IMP-SAF-002

## Objective

Make the existing Mission Checks workflow an authoritative operational decision engine. It must produce immutable evidence, automatically create the controls implied by unsafe answers, support Pilot in Command self-approval for Production Beta, and give Mission Readiness precise reasons why authorisation is or is not permitted.

The JSA remains inside the existing Mission planner. It is not a standalone application and the existing questions, layout, terminology, workflow and unsafe-answer polarity are preserved.

## Authoritative aggregate

The authoritative aggregate has two independent version streams.

### Platform JSA template versions

A platform-controlled template version contains:

- stable template and question identifiers;
- question text, display order and mandatory state;
- unsafe-answer polarity;
- risk category;
- rule-driven visibility conditions;
- the specification for any control generated by an unsafe response;
- attachment requirements; and
- effective and retired timestamps.

Published versions are immutable. Existing Mission revisions always resolve against the exact version referenced when saved.

### Platform Hazard Library

Platform-controlled, versioned hazard definitions provide stable operational hazard identity independently of JSA templates. Each hazard version contains:

- stable Hazard ID and version number;
- hazard name and description;
- category;
- typical controls;
- applicable jurisdiction;
- authoritative references;
- related regulations where applicable;
- provenance, publication and retirement metadata.

Templates reference stable platform hazards and the exact minimum hazard version they were designed against. A Mission JSA revision creates a versioned Mission hazard instance containing the platform Hazard ID, hazard-version reference and a complete planning-time snapshot. Later platform corrections or improvements never rewrite the Mission instance.

### Mission JSA revisions

Every Draft save creates an immutable Mission JSA revision. A revision references the Mission, organisation, operating location, template version, organisation policy version, creating user and creation time. It stores complete response, hazard, control, attachment and approval snapshots.

Optimistic concurrency compares the submitted expected revision with the current Mission JSA revision. A stale command fails atomically and creates no revision, audit event or outbox event.

## Rule-driven conditional questions

Template rules determine which questions and sections apply. Rules operate only on declared Mission facts and JSA answers using a bounded expression model such as `all`, `any`, `equals`, `notEquals`, `in` and `answeredUnsafe`. Rules never execute arbitrary code.

The rule engine returns the applicable question set and generated controls deterministically for a given template version, Mission facts and response set. Night operations, chemicals near water, powerlines and forestry are template data, not conditional branches embedded in React or business services.

An applicable mandatory question must be answered. A hidden or inapplicable question cannot block readiness and remains visible only in historical revisions where it previously applied.

## Responses and hazards

Each response snapshot records the question identifier, rendered question text, answer, notes, mandatory state, unsafe polarity, applicability result and rule evaluation provenance.

Each unsafe response creates a Mission hazard instance with its own stable ID, the referenced Platform Hazard ID and version, the complete platform hazard snapshot, triggering question, risk category, initial likelihood, initial consequence and calculated initial score. Operators may add notes and assess the generated hazard, but do not manually recreate hazards already implied by the template.

## Triggered risk controls

The server derives required controls from unsafe responses. Each control snapshot contains:

- stable control and template-control identifiers;
- triggering question and hazard;
- risk category;
- required mitigation description;
- assigned authoritative Personnel owner and Personnel version snapshot;
- due status and completion state;
- completion timestamp and completing Personnel snapshot where required;
- initial and residual likelihood, consequence and score;
- evidence as internal file IDs and immutable file-version references;
- operational notes; and
- derivation provenance.

The client may submit assessments, ownership, mitigation, completion and evidence. It cannot suppress a required server-generated control or manufacture a template control that is not applicable.

### Platform Operational Knowledge

Mission controls and their mitigation text are immutable historical evidence owned by the Mission revision. They are never used as mutable shared templates.

A separate Platform Operational Knowledge domain may receive proposed improvements derived from completed Mission controls. Promotion is an explicit platform research and approval workflow that stores provenance back to the originating Mission evidence where permitted. Approval publishes a new version of operational knowledge; it does not change the originating Mission, other historical Missions, platform hazard versions or published JSA template versions.

## Risk calculation and readiness threshold

The existing 1–5 likelihood and 1–5 consequence values and multiplicative score are preserved. The organisation JSA policy version defines the maximum acceptable residual score, defaulting to less than 6 for Production Beta.

For a triggered control with initial score of 6 or more, mitigation, an owner and a residual assessment are mandatory. Where the policy or template marks completion as required before authorisation, the control must also be complete with any mandatory evidence attached. A residual score at or above the configured threshold blocks Mission Authorisation.

## Approval policy

Organisation-owned, versioned JSA policies define approval requirements. The Production Beta default is `PIC_SELF_APPROVAL`.

The policy model supports these rule types without changing the Mission workflow:

- `PIC_SELF_APPROVAL`;
- `PIC_PLUS_REVIEWER`;
- `DUAL_APPROVAL` with named permission or operational-role requirements;
- `RISK_BASED`, selecting required approval roles from the highest applicable risk band; and
- organisation-defined combinations of approver role, permission, count and separation-of-duties constraints.

Approver identities are never hard-coded. Approval commands resolve authoritative Mission Personnel assignments and permissions. Under Production Beta policy, the approving person must be the current assigned PIC and the authenticated member must be linked to that Personnel record. Free-text approval identities are prohibited.

An approval snapshot retains Personnel ID, Personnel version, assignment role, relevant credential snapshot, linked internal user, policy requirement satisfied and approval timestamp.

## Attachments

JSA and control attachments use internal file IDs rather than provider URLs. Each reference records the internal file version, checksum, evidence type, access classification, attaching user, attachment timestamp and provenance. Template and policy rules decide whether an attachment is mandatory.

## Mission Readiness contract

The JSA readiness evaluator returns an overall readiness state, structured `blockers`, structured `warnings`, grouped readiness categories, outstanding sections, completed sections, the evaluated JSA revision, template version and policy version. The overall state is one of `NOT_STARTED`, `INCOMPLETE`, `BLOCKED`, `WARNING`, or `READY`. It evaluates:

- a current JSA revision exists;
- every applicable mandatory question is answered;
- every mandatory hazard is assessed;
- every required control was generated;
- control ownership is assigned;
- required mitigation and residual assessment are present;
- required controls are complete;
- residual risk is below the organisation threshold;
- required attachments exist;
- required approvals exist; and
- every organisation policy rule is satisfied.

Every blocker and warning contains a stable code, human explanation, readiness category and related question, hazard or control identifier where applicable. Categories group results under Questions, Hazards, Controls, Attachments, Risk and Approval. `outstandingSections` lists every category with unresolved blockers or warnings; `completedSections` lists every applicable category whose mandatory checks pass. The evaluator never returns only “Ready” or “Not Ready.”

## Mission Authorisation boundary

Mission Authorisation is a later package. Its contract accepts only a specific approved JSA revision. The authorisation snapshot permanently embeds or references immutable evidence for the JSA revision, template version, policy version, responses, hazards, controls, attachments, PIC snapshot and approval timestamp.

Editing a JSA after Mission Authorisation creates a new revision. It never updates the revision retained by an authorised Mission and cannot silently change historical authorisation evidence.

## API and database boundaries

Versioned `/api/v1/mission-jsa` routes delegate to JSA application and repository services. Transport code performs request-shape checks and permission checks but contains no rule, risk or approval logic.

Trusted PostgreSQL commands own version creation and approval transactions. Server authorisation and PostgreSQL RLS enforce organisation and operating-location isolation. Repository-controlled migrations own all tables, constraints, functions, policies, triggers and grants.

Production Beta permissions include:

- `mission.jsa.read`;
- `mission.jsa.write`;
- `mission.jsa.approve`; and
- future reviewer permissions referenced by organisation policy.

Default organisation administrators receive read/write operational permissions. Approval is granted through role administration and PIC assignment/policy checks; the generic administrator role does not bypass the assigned-PIC requirement.

## Audit and event delivery

JSA revision save and approval actions write append-only audit events and transactional outbox events in the same database transaction. Events identify the Mission, revision, template version, policy version, actor, approving Personnel and readiness result without exposing restricted attachment content.

## Failure behaviour

Invalid answers, incomplete mandatory data, unknown template items, missing owners, unacceptable residual risk, unlinked PIC identity, location denial, tenant denial and stale versions fail visibly. A failed command creates no partial revision, approval, audit record or outbox event. The frontend never substitutes MissionContext, local storage or legacy JSA persistence.

## Production Beta acceptance

1. The deployed existing Mission Checks interface opens inside the accepted real Mission.
2. Safe and unsafe answers persist in an immutable PostgreSQL JSA revision.
3. Unsafe answers generate the correct required controls using existing answer polarity.
4. Ownership, mitigation, residual risk, completion, evidence and notes persist.
5. Readiness explains all incomplete, control, residual-risk, attachment and approval blockers.
6. The assigned member-linked PIC can approve under `PIC_SELF_APPROVAL`; a non-PIC cannot.
7. Approval retains the PIC Personnel and credential snapshot plus template and policy versions.
8. Refresh, re-login and an authorised second session reopen identical evidence.
9. A stale update conflicts; tenant and operating-location access is denied.
10. Audit and outbox records exist and no browser or legacy persistence fallback occurs.
11. A later revision does not mutate the approved historical revision.

## Out of scope

Overall Mission Authorisation, Mission Pack generation, enterprise reviewer assignment UI, promotion into Platform Operational Knowledge and automated external safety-regulation ingestion remain separate packages. The JSA data and readiness contracts must support them without schema redesign.
